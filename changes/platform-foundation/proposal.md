# 项目基础整合与跨端演进提案

本提案描述目标态；在被接受并进入当前范围前，不代表当前实现或实施授权。当前版本边界以 [SCOPE.md](../../SCOPE.md) 为准。

## Why

项目已有鲜明的木质展柜、信件、相纸和节日叙事，产品概念明显强于普通模板站；问题主要来自发布边界、共享契约和工程门禁没有跟上页面数量增长。

本次审查的关键证据：

- `master` 与 `origin/master` 同为 `8eb34f3`，七夕源码和集成改动只存在于本地工作树。
- 七夕只受日期门禁控制；当前日期已过 `2026-08-19`，生产构建成功并包含 `QixiPageLoader`、七夕 CSS 和照片资源，存在误发布风险。
- 本地测试工具被 `.gitignore` 排除，但项目规范又将其描述为年度维护入口，协作语义冲突。
- 路由、标题、懒加载、访问控制、档案数据和沙漏的“已建页面”列表分散；`ViewState` 与 `AppView` 重复，新增节日需要多点手工同步。
- 108 个前端源文件中出现约 968 次十六进制色值、252 个不同色值和 212 次任意像素值；共享主题令牌存在，但没有成为稳定的视觉契约。
- 生产构建的主入口约 1.69 MB，端午页面脚本约 418 KB；仓库还包含 3–5 MB SVG 与 7 MB 级音频。移动网络和旧设备压力明显。
- 当前没有自动化测试或 CI；TypeScript 未启用 `strict`。`npm run lint` 和 `npm run build` 当前均通过。
- 静态部署没有登录与服务端授权。若“私密纪念站”意味着内容不可公开访问，现架构不能提供隐私保证。
- 静态检测器以降级模式运行，仍报告 12 项字体、配色、灰字对比和回弹动效问题；实际问题只会被低估，不应把旧审计中的空检测结果当作现状。

源代码技术审计暂定为 9/20：无障碍 2/4、性能 2/4、响应式 2/4、主题 1/4、实现完整性 2/4。优势是 `100dvh`、safe area、路由懒加载、页面资源预载和部分专题页的 reduced-motion 已有良好基础。

## Scope

- 建立机器可验证的草稿、预览、已发布生命周期，先消除七夕误发布风险。
- 收敛路由、节日注册、标题、访问、档案入口与懒加载的重复事实源。
- 形成 Web-first 的跨设备适配标准，覆盖 iOS Safari、Android Chrome、macOS Safari/Chrome 和桌面浏览器。
- 建立统一但允许专题差异的设计系统，强化真实手作感并清除通用 AI 模板语法。
- 把本地 TS/JSON 内容读取收口到仓储接口，为以后接入 API、数据库和对象存储留出替换点。
- 分离源码与发布产物，补齐质量门禁、文档治理和隐私边界。

## Non-goals

- 本提案不直接完成七夕视觉与文案。
- 当前阶段不选定后端供应商，不创建数据库，也不开发 iOS/Android 原生客户端。
- 不做一次性大重写；迁移应保持现有 URL 和页面体验可回退。
- 不强制所有节日页使用同一配色或构图，只统一外壳、交互和质量底线。

## 目标架构

### 1. 发布与页面生命周期

- 建立唯一的页面/节日注册表，至少包含 `id`、`route`、`title`、`lifecycle`、`opensAt`、`loader`、档案元数据和资源预算。
- `lifecycle` 使用 `draft`、`preview`、`released`、`archived`；日期只决定已发布页面何时开放，不能把草稿自动变成正式页面。
- 生产构建只解析 `released` 页面。`draft` 页面、私密素材与调试工具必须从构建图中排除，而不只是隐藏入口。
- 七夕在完成验收前固定为 `draft`；发布动作必须显式改状态并通过产物检查。

### 2. 前端模块边界

- `app/` 只负责启动、壳层、导航与页面注册，不再在 `App.tsx` 手写每个节日分支。
- 现有展柜、信件、相册、相恋时光和节日页面按 feature 维持自治；共享层只放真正跨 feature 的布局、UI、主题、动效、加载和类型。
- 每个节日模块通过同一契约暴露 loader、访问策略、档案信息和可选专题主题；沙漏、档案馆和路由只消费注册表。
- 拆分 `FestiveHourglass.tsx`、`cabinetDecorComponents.tsx` 等超大文件，把节日数据、图形、交互和日期计算分开测试。
- `src/dev-only/` 的工具代码应纳入版本控制，并由 `import.meta.env.DEV` 保证生产排除；只有个人状态与覆盖值留在本地。

### 3. 多设备与 PWA 策略

- 先保持响应式 Web/PWA 单代码库。只有出现推送、系统分享、后台同步、相机深度接入等明确需求时，再评估原生壳。
- 布局以能力和可用空间为依据，不按品牌机型写分支；至少覆盖 320–430px 手机、600–1024px 平板、桌面窄窗、横屏和 200% 文字缩放。
- 保留 `dvh` 与 safe area；移除 `user-scalable=no`，统一 44px 触控热区、键盘焦点、语义按钮、滚动责任和 reduced-motion。
- PWA 若要宣称“可安装/近离线”，需把 manifest 的 `display`、图标、安全缓存与更新策略作为完整能力交付；目前只能称普通 Web 应用。

### 4. 统一且有手作感的视觉系统

- 在根目录建立 `DESIGN.md`，把“温柔、私密、手作”转成可验证规则：材料、字体角色、纸张与木色、间距、圆角、动效、声音和禁用模式。
- 采用三层令牌：全站基础令牌、共享组件语义令牌、专题页作用域令牌。专题可以不同，但返回按钮、焦点、加载、错误、静音和安全区行为一致。
- 替换或弱化 `Plus Jakarta Sans + Space Grotesk + Playfair Display`、全大写宽字距眉标、无意义玻璃模糊、紫色渐变和弹跳动画等常见生成式模板语法。
- “手作感”来自真实私人内容、克制的不规则边缘、扫描笔迹或有来源的字形、材料纹理和物理一致的动效，不依赖堆叠滤镜与随机装饰。

### 5. 后端与数据扩展缝

- 先定义领域模型：`CoupleSpace`、`Memory`、`Letter`、`Album`、`MediaAsset`、`FestivalPage`、`Release`；业务组件不直接依赖数据库字段。
- UI 只调用仓储接口，例如读取信件、相册、节日与媒体；第一版由本地 TS/JSON adapter 实现，未来替换为 HTTP adapter 时页面无需重写。
- API DTO 必须版本化并在边界校验；数据库记录保存元数据和权限，图片/音频进入对象存储，避免把大二进制塞进数据库。
- 所有核心记录带 `spaceId`、稳定 ID、创建/更新时间、排序和可见性。服务端负责鉴权、授权和发布状态；客户端日期门禁不能承担安全职责。
- 在真正接入后端前先确定隐私目标、备份与恢复、数据导出、删除策略、时区和媒体 EXIF 清理要求。

### 6. 仓库与文档治理

- 根 `README.md` 只保留项目入口、运行方式、发布方式和文档地图；详细架构迁入 `docs/ARCHITECTURE.md`。
- 根 `SCOPE.md` 是唯一当前范围权威。把 `Cabinet/PRODUCT.md` 迁到根 `PRODUCT.md`，并补根 `DESIGN.md`。
- 用根 `AGENTS.md` 合并 `.cursor/rules/project-guidelines.mdc` 与 `Cabinet/docs/PROJECT-GUIDELINES.md` 的长期规则，避免双写漂移。
- 保留 `RESOURCE-LOADING-GUIDELINES.md` 作为专项契约；刷新 `UI-AUDIT.md` 的日期、检测结果和状态。
- 明确 `story/` 是仍维护的独立体验还是历史原型；若是历史内容，移出发布根并标为 `historical`。
- 推荐由 CI 构建并发布 `Cabinet/dist` 到独立部署产物或部署分支，不再把生成的 `assets/` 与源码长期混在同一开发分支。
- 暂不创建 `CONTRIBUTING.md`；当前没有多 Owner 协作证据。后端或多个独立维护单元出现后，再增加 `CONTRACT.md` 与 ADR。

## 受影响边界

- 应用壳与导航：`Cabinet/src/app/`。
- 节日共享契约：`Cabinet/src/pages/festivals/`、沙漏与档案馆。
- 视觉与跨端基础：`Cabinet/src/shared/`、`Cabinet/src/index.css`、两个 HTML 入口。
- 内容与未来数据层：信件、相册、纪念日、节日及媒体资源。
- 构建与部署：`Cabinet/vite.config.ts`、`Cabinet/scripts/copy-site.mjs`、仓库根发布产物。
- 项目治理：根 README、范围、产品、设计、架构、Agent 规则与变更记录。

## 风险与回退

- 注册表迁移可能导致旧 hash 失效；保留现有 hash 映射与重定向，并可按模块回退。
- 发布产物分离会改变现有 Pages 流程；在新流程验证前保留 `build:site`，但禁止其发布草稿。
- 令牌收敛可能削弱专题个性；先迁移共享外壳，再逐页视觉回归，不做全站一次性替换。
- 数据仓储抽象可能过度设计；第一阶段只覆盖已有读取场景，不引入未使用的通用层。
- 私密内容迁移需要可逆备份；上线后端前完成导出、恢复和权限测试。

## 验收

- 生产构建不包含任何 `draft` 页面代码、样式和媒体；七夕发布必须经过显式状态变更。
- 新增节日只修改一个注册入口和节日本身，不再同步五处字符串列表。
- 指定设备矩阵无横向溢出、焦点丢失、缩放锁定或小于 44px 的主要交互热区。
- 主入口与重型专题满足任务清单中的资源预算，慢速网络有可理解的加载与失败恢复。
- UI 可以在不改页面组件的情况下切换本地仓储与未来 HTTP 仓储。
- 当前范围、目标态、历史版本和本地测试能力在文档中各有明确位置且无冲突链接。
